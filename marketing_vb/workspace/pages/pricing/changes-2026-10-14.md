# 3DLOOK Pricing page: proposed changes (2026-10-14)

**Page:** https://3dlook.ai/pricing/ · **Prototype:** [3DLOOK pricing page prototype 2026-10-14.html](https://drive.google.com/file/d/1cKWDpyOOR3VpDphk1xWQ3h0LgtPxUqfg/view) (download and open in a browser; both tabs work, including the Monthly/Annual switch)
**Inputs:** Vadim's brief in #marketing (10-14), Nika's and Asselya's proposals in the same thread, Asselya's Doc [FitXpress - Pricing page tab](https://docs.google.com/document/d/1zs-D7g55B2y8Vady64sDuglN7JnVc3_8geeFM3U7pCc/edit?tab=t.9vpq8kz8oyzz), Kateryna Boichuk's billing explanation, the public API docs ([docs.fitxpress.3dlook.me](https://docs.fitxpress.3dlook.me/), section Subscription), GA4, Search Console, Microsoft Clarity and Ahrefs for /pricing/.

## 1. Summary

- **Why the page has to change.** FitXpress is billed per API request, while the page sells "scans". The API counts four request types against one pool: body scan, 3D goal model, 3D progress comparison and 2D progress images. A Pro client who scans 1,000 people and shows each a progress comparison uses about 2,000 requests, while the card promises "up to 1,000 scans". Mobile Tailor is billed per successful scan, and that part of the page is correct.
- **The new page leads with the product choice.** Each product card shows who it is for and how it is billed. 38% of /pricing/ views come from Mobile Tailor pages, yet the page opens on FitXpress for 92% of them.
- **The FitXpress tab now explains the unit.** Volumes are stated in API requests. Billable features carry a "1 request" tag. A table shows what each request returns, and two worked examples show how a pharmacy and a weight-management program would size a plan.
- **Several claims on the live page are removed or corrected.** The page says "Sign up for a 7-day trial" under FitXpress (meta description, schema and footer) and that FitXpress "maintains HIPAA compliance". It also quotes "95%+ repeatability", gives two processing times (40 and 45 seconds) and claims "over 80 long-term customers".
- **Five decisions are needed before launch** (section 6). The most important one is whether progress tracking and goal visualization stay Pro-only. Sales says every plan has always had every feature.

## 6. Decisions needed before launch

| # | Question | Who | Prototype default |
|---|---|---|---|
| 1 | **Feature gating.** Kateryna says FitXpress is billed per request on every plan, and plans used to differ only in volume. The page gates progress tracking and goal visualization to Pro, a split agreed when the page was built so the plans would look different. If sales sells every feature on every plan, the page contradicts the contract. | Vadim and sales | Gating kept, as agreed. If sales does not enforce it, switch to "every plan includes every output; plans differ by volume and support". That means changing the cards and two table rows. |
| 2 | **What happens at the limit.** Our internal pricing note says extra requests are billed at the plan rate. The API docs say requests return an error (403) once the limit is reached. | Sales and product | The page says neither. The FAQ only explains how to track usage. |
| 3 | **Is each billable action exactly one request?** This covers the 3D goal model, 3D progress and 2D progress. Are 2D progress images on Pro, like 3D? Is the pool monthly on annual plans? The API gives the subscription an end date. | Product | One request each. 2D is on Pro and Personalized. The pool is monthly. |
| 4 | **Failed scans.** Our sales answer says failed-due-to-pose scans are not billable. On 09-30 Vadim decided this stays a sales answer and does not go on website pages. | Vadim | Not on the page |
| 5 | **Smaller confirmations.** Does Smart Scales still need a "beta" label (tech spec says beta)? Does the Mobile Tailor trial cost $1 (HubSpot plan "smb_free7_dollar")? If so, the button should say "7-day trial for $1". Is "We respond within one business day" a commitment sales keeps? | Product, Mobile Tailor team, sales | No beta label. "Start a 7-day trial". The one-business-day line is kept from the live page. |

## 7. Technical fixes for the developer

1. Render each plan card once. The live HTML has every card twice under a duplicate id, so every plan heading appears twice.
2. Remove the hidden Mobile Tailor hero that sits at opacity 0 over the FitXpress hero.
3. Load the HubSpot demo form once, when a CTA is clicked, instead of four embeds on page load. Since 10-02, `form_start` fires about four times per view (2,132 events from 457 users), which makes the event useless.
4. Fix the header items "Use Cases", "Made-to-Measure", "Resources" and "About 3DLOOK", which link to "#" (12 real Clarity sessions on /pricing/# in 72 h).
5. Point the header "Pricing", the Mobile Tailor menu "Pricing", Mobile Tailor pages and the chatbot "7-day trial" branch to the right ?product= link.
6. Tracking: the prototype puts `data-event-name` on every CTA, product switch and billing switch. The `plan` parameter of `pricing_plan_click` currently records button or menu text and needs the plan name. Add a click event for the Mobile Tailor sign-up links (mtm.3dlook.me), which GA4 doesn't see today.
7. In Yoast, set og:type to "website" and replace the meta and OG descriptions.
8. Script errors in about 20% of sessions don't reproduce in a clean headless load, so they most likely come from third-party scripts (OptinMonster, Hotjar, chat, Clearout, four forms). Check them in Clarity recordings filtered to /pricing/ with "script error".

## 8. How to measure the result

Compare 30 days after launch with the baseline above:
- FitXpress `demo_click` per plan (baseline: 21 in the first 6 days of tracking) and form submits on the page (13 to 20 a month in July to September)
- The share of visitors arriving from Mobile Tailor pages who see the Mobile Tailor tab first (baseline: 144 of 1,806, about 8%)
- Clicks to the Mobile Tailor sign-up (baseline: not tracked)
- Clarity: desktop dead clicks (baseline 10% of sessions) and script errors (baseline about 20%)
- Exits from /pricing/ to /technology/ and FitXpress pages. If the FAQ works, fewer visitors should need to leave to find answers.
