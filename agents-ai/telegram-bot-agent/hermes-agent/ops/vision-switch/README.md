# vision-switch — читатель картинок берётся напрок, на один ход

## Зачем

Раньше «модель дня» обязана была уметь читать картинки, и это стоило мозгов:
типичное утро — сильнейшая бесплатная модель 82, сильнейшая **видящая** 62.
Носить слабую модель весь день ради редкого скриншота — плохой обмен.

Теперь роли разведены:

| приходит | кто отвечает |
|---|---|
| текст | сильнейшая бесплатная модель дня (может быть text-only — это нормально) |
| текст + картинка | сильнейшая модель, **доказавшая** что видит — только на этот ход |
| снова текст | автоматически обратно на сильнейшую |

Возврат не требует ни команды, ни подтверждения: он в `finally` хода.

## Как устроено

Утренний роутер (`ops/model-router/refresh.py`) кладёт в `pick.json`:

```json
{ "primary": "nemotron-3-ultra-free",
  "best_vision": "mimo-v2.5-free",
  "best_vision_provider": "opencode-zen",
  "best_vision_verified_today": true }
```

`best_vision` — не то, что модель заявила о себе в каталоге, а то, что она
доказала: ей показывают PNG 8×8 чистого красного и просят назвать цвет
(`vision_ok` в `router_lib.py`). Он же пишется в `config.yaml` →
`auxiliary.vision`.

`vision_switch.py` вешается на два места в `gateway/run.py`:

1. **engage** — внутри `_prepare_inbound_message_text`, там где нашлись
   входящие картинки. Ставит per-session model override на читателя и
   сбрасывает закешированного агента.
   Критично, что это **до** `_decide_image_input_mode`: тот вызов резолвит
   override сессии и решает, отдать модели пиксели (`native`) или чужое
   текстовое описание. Переключиться после него — значит переключиться зря.
2. **release** — в `finally` обработки сообщения, рядом со штатными
   восстановлениями MoA и `/model --once`. Отрабатывает при успехе, исключении
   и прерывании одинаково.

Переключение — это override + пересборка агента (тот же шов, что у `/model` и
у heavy mode), **не** переписывание `config.yaml`: тому нужен рестарт шлюза, а
шлюз в этот момент отвечает на сообщение.

## Что будет, если что-то сломается

Ни один сбой не стоит хода — деградация, а не отказ:

* роутер не отработал / сегодня никто не прошёл vision-пробу → `engage` молча
  ничего не делает, картинку опишет `auxiliary.vision` штатным путём Hermes;
* модель дня сама умеет видеть → переключаться не на кого, `engage` — no-op;
* у пользователя стоял свой `/model` → он восстановится ровно как был
  (`release` кладёт назад снимок, а не «дефолт»);
* ход закончился под другим routing key, чем начался (Telegram может
  переклеить topic на лету) → `release` всё равно найдёт захват **по asyncio-таске**,
  которая его сделала.

⚠️ Освобождается только **своё**. `release` висит в `finally` каждого хода, а не
только «картиночного», и шлюз обслуживает все чаты одним event loop. Слепая
зачистка «освободить всё занятое» означала бы, что безобидное «ок» в чате B
отбирает читателя у чата A, пока тот ещё ждёт маршрутизацию картинки: ход A уже
уехал в режим `native`, и пиксели ушли бы слепой модели. Поэтому владение
отслеживается, а не угадывается. Отдельно подметаются захваты, чья таска
завершилась не освободившись, — это единственный способ залипнуть.

Картинка остаётся в истории диалога. Когда следующий текстовый ход уходит на
text-only модель, провайдер отобьёт её — upstream ловит это сам, вырезает
image-части и повторяет запрос (`agent/conversation_loop.py`). Одна лишняя
попытка вместо переписывания транскриптов из патча. Ответ читателя при этом
остаётся в истории обычным текстом — именно его и читают уточняющие вопросы.

## Установка / переустановка

```bash
python3 ops/vision-switch/apply-vision-switch-patch.py
systemctl --user restart hermes-gateway.service
```

Идемпотентно. Код возврата `2` = анкер в `run.py` сместился (upstream
переписал это место) — патч НЕ применён, нужен фикс патчера.
`ops/hermes-update.py` переприменяет патч после каждого `hermes update`
(апстрим-переустановка сносит вендоренные файлы) и пишет в Telegram, если
анкер уехал.

## Проверить, что работает

```bash
# что выбрано сегодня
python3 -c "import json;d=json.load(open('$HOME/.hermes/model-router/pick.json'));print(d['primary'],'|',d['best_vision'])"

# сам факт переключения — в логах шлюза
journalctl --user -u hermes-gateway -f | grep vision-switch
```

В логе на картинке будет `vision-switch: <рабочая> → <читатель> на один ход`,
и следом `vision-switch: вернул рабочую модель на сессии …`.
